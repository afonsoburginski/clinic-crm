# Clinic API

- Purpose: Villiére HTTP API using Hono on Bun and PostgreSQL persistence.
- Entrypoint: `backend/src/main.ts`; scripts: `bun run dev`, `bun test`, `bun run typecheck`.
- Data design: don't partition OLTP entities speculatively. Use time partitioning for append-heavy audit/events and dashboard read-models only when query shape, retention, and uniqueness are specified; dashboard aggregates should have explicit period/tenant keys and indexes.
- Current code map: `presentation/app.ts` composes the API router in `presentation/routes/api.ts`; handlers are still concentrated in that router. Pure scheduling rules live in `domain/appointments.ts`; financial rules live in `domain/financial.ts`. Catalog (professionals, specialties, services, rooms, settings, audit log) follows ports/use-cases/repository: `application/ports/catalog.ts`, `application/use-cases/catalog.ts`, `infrastructure/postgres/repositories/catalog.ts`, wired in `presentation/composition/catalog.ts`. Clinical records and assessments follow the same layout (`ports/{clinical-records,assessments}.ts`, `use-cases/{clinical-records,assessments}.ts`, `repositories/{clinical-records,assessments}.ts` over the shared `repositories/api-resources.ts` SQL, wired in `presentation/composition/`); the professional-patient access check is the `PatientAccessPolicy` port (`ports/patient-access.ts`), bound to `assertProfessionalPatientAccess` in `composition/patient-access.ts`. ABA, financial and documents follow the same layout (`ports/{aba,financial,documents}.ts`, `use-cases/{aba,financial,documents}.ts`, `repositories/{aba,financial,documents}.ts`, wired in `presentation/composition/`): their repositories run decisions under the row lock through `changeLockedResource` (`repositories/api-resources.ts`), the pure goal-progress rules live in `domain/aba.ts` and the pure financial rules stay in `domain/financial.ts`. Documents gate list reads by classification through the `PermissionPolicy` port (`ports/permissions.ts`, bound to `hasPermission` in `composition/permissions.ts`). The one known legacy gap left in these three domains (a client-sent `status`/`createdBy` honored at creation) is isolated in `use-cases/legacy-defaults.ts`; professional lists are scoped through `professionalScopeOf` (a professional without a link gets `forbidden`), generic updates refuse the fields owned by the dedicated actions (`status`/`releases` on documents, `status`/`payments` on financial entries), document reads by id apply the classification permission, and `updateGoal` re-validates the merged goal. `registerResource`/`registerActions` in `routes/shared.ts` and the god service in `application/resources.ts` are no longer used by these routers (`routes/auth.ts` still calls `getResource`).
- `shared/contracts/src/api.ts` contains framework-independent data types; route inventories are deliberately not duplicated there.
- ORM: Drizzle (`drizzle-orm`, driver node-postgres sobre o `pool` único de `infrastructure/database.ts`; `drizzle-kit` em dev). Todo código novo de persistência usa Drizzle atrás de ports: `infrastructure/postgres/schema.ts` (espelho tipado das migrations 001–007), `infrastructure/postgres/drizzle.ts` (`db()`), repositórios em `infrastructure/postgres/repositories/`. Os repositórios antigos (`pg` cru em `api-resources.ts` etc.) só migram quando forem alterados. Migrations: SQL manual em `backend/migrations/00N_*.sql` (fonte do que existe) + journal Drizzle em `backend/migrations/drizzle/` com baseline sem efeito; scripts `bun run db:generate | db:migrate | db:check` (ver `backend/README.md`, "Migrações").
- Usuários, papéis e permissões vivem no banco (migration `006_users_roles_permissions.sql`). `domain/permissions.ts` é a única fonte dos padrões (catálogo + papéis de sistema); a matriz editável fica em `role_permissions` por clínica, semeada de forma idempotente no primeiro uso (`UserDirectory.ensureReady`), que também importa `AUTH_USERS_JSON` para uma clínica sem usuários. Layout: `ports/users.ts`, `use-cases/users.ts` (+ `provisioned-users.ts`), `repositories/users.ts` (Drizzle), `composition/{users,auth}.ts`, `routes/users.ts`. `application/auth.ts` virou `createAuth({ directory, sessions, env })` (sessões/lockout em `repositories/auth-sessions.ts`); a sessão devolve `permissions` efetivas e o guard (`routes/auth.ts`, `createAuthRouter`) usa `user.permissions`. Regra RN-AUTH-002 mantida: nunca `clinical:*` para quem tem o papel `admin`. Spec: `backend/specs/users-roles.spec.md`.
- Preferências de tabela por usuário (migration `007_table_preferences.sql`, spec `backend/specs/table-preferences.spec.md`): visões salvas (tamanho de página, ordenação, colunas, filtros) em `user_table_preferences`, sempre do usuário da sessão. Layout: `domain/table-preferences.ts` (validação), `ports/table-preferences.ts`, `use-cases/table-preferences.ts`, `repositories/table-preferences.ts` (Drizzle), `composition/table-preferences.ts`, `routes/table-preferences.ts`. As rotas `/api/v1/preferences/tables/...` exigem só sessão (`AUTHENTICATED` em `permissionFor`); o resto de `/preferences` segue negado.
- Relatório, busca e exportação financeira (migration `008_finance_export.sql`, spec `backend/specs/financial-report.spec.md`): `GET /financial/{report,entries/search,export}` em `routes/financial-report.ts` (montado antes de `routes/financial.ts` para `search` não virar `:id`). Layout: `domain/financial-report.ts` (filtros, derivação, indicadores, séries, busca, tudo TS puro), `ports/financial-report.ts`, `use-cases/financial-report.ts`, `repositories/financial-report.ts` (Drizzle sobre `api_resources`, só filtros baratos; chaves JSON como literais SQL, nunca parâmetro), `composition/financial-report.ts`. Nova permissão `finance:export` (padrão de `admin` e `finance`); a exportação é auditada (`action=export`, só a contagem) e tem teto de 10 000 linhas.
