# Clinic API

- Purpose: Villiére HTTP API using Hono on Bun and PostgreSQL persistence.
- Entrypoint: `backend/src/main.ts`; scripts: `bun run dev`, `bun test`, `bun run typecheck`.
- Data design: don't partition OLTP entities speculatively. Use time partitioning for append-heavy audit/events and dashboard read-models only when query shape, retention, and uniqueness are specified; dashboard aggregates should have explicit period/tenant keys and indexes.
- Current code map: `presentation/app.ts` composes the API router in `presentation/routes/api.ts`; handlers are still concentrated in that router. Pure scheduling rules live in `domain/appointments.ts`; financial rules live in `domain/financial.ts`. Catalog (professionals, specialties, services, rooms, settings, audit log) follows ports/use-cases/repository: `application/ports/catalog.ts`, `application/use-cases/catalog.ts`, `infrastructure/postgres/repositories/catalog.ts`, wired in `presentation/composition/catalog.ts`. Clinical records and assessments follow the same layout (`ports/{clinical-records,assessments}.ts`, `use-cases/{clinical-records,assessments}.ts`, `repositories/{clinical-records,assessments}.ts` over the shared `repositories/api-resources.ts` SQL, wired in `presentation/composition/`); the professional-patient access check is the `PatientAccessPolicy` port (`ports/patient-access.ts`), bound to `assertProfessionalPatientAccess` in `composition/patient-access.ts`. ABA, financial and documents follow the same layout (`ports/{aba,financial,documents}.ts`, `use-cases/{aba,financial,documents}.ts`, `repositories/{aba,financial,documents}.ts`, wired in `presentation/composition/`): their repositories run decisions under the row lock through `changeLockedResource` (`repositories/api-resources.ts`), the pure goal-progress rules live in `domain/aba.ts` and the pure financial rules stay in `domain/financial.ts`. Documents gate list reads by classification through the `PermissionPolicy` port (`ports/permissions.ts`, bound to `hasPermission` in `composition/permissions.ts`). The one known legacy gap left in these three domains (a client-sent `status`/`createdBy` honored at creation) is isolated in `use-cases/legacy-defaults.ts`; professional lists are scoped through `professionalScopeOf` (a professional without a link gets `forbidden`), generic updates refuse the fields owned by the dedicated actions (`status`/`releases` on documents, `status`/`payments` on financial entries), document reads by id apply the classification permission, and `updateGoal` re-validates the merged goal. `registerResource`/`registerActions` in `routes/shared.ts` and the god service in `application/resources.ts` are no longer used by these routers (`routes/auth.ts` still calls `getResource`).
- `shared/contracts/src/api.ts` contains framework-independent data types; route inventories are deliberately not duplicated there.
